## Decisão revisada — limites proporcionais

A revisão anterior foi excessiva ao converter ausência de confirmação documental nesta pesquisa em bloqueio geral dos produtos e do registro operacional. Essa conclusão foi corrigida. **Consulta MAPA indisponível não comprova irregularidade; status curatorial do software não é situação de registro no MAPA.** O usuário informou que os produtos utilizados já são autorizados. Essa informação orienta o escopo operacional, sem ser apresentada como verificação independente de cada registro nesta pesquisa.

O app deve registrar uma aplicação já realizada com seus dados reais. Na conclusão manual da Agenda, a UI agora declara `registrationMode=executed_fact`; o core exige confirmação explícita, data não futura, identidade/vínculos coerentes, fazenda correta, dose/unidade/via e controles de estoque. Curadoria pendente, protocolo draft/retired ou restrição contextual permanecem como sinais auditáveis do registro, sem apagar o fato ou conceder autorização para nova aplicação. Um produto com dados técnicos pendentes permanece selecionável para esse registro, com aviso.

O modo anterior sem essa declaração mantém a barreira de catálogo para uso prospectivo. O novo registro persiste `prospective_authorization=false`, não aprova nem ativa catálogo e não cria recomendação clínica. Reprocessamento continua idempotente; fato e estoque/fila permanecem atômicos. Carência desconhecida permanece desconhecida: **não impede registrar a aplicação; impede inventar prazo zero ou declarar livre de carência.**

Os 10 protocolos e 53 verificações continuam reavaliados. Os estados `draft`, `retired`, flags e payload candidato não foram ativados/importados. A impossibilidade de executar Supabase nativo aqui é uma limitação da validação desta entrega, não uma prova de defeito em produção ou de impedimento regulatório dos produtos.

## Reprodução da verificação SQL isolada

O harness `tests/codex/sanitario-v2-pglite.integration.mjs` cria seu próprio banco novo em memória, aplica quatro migrations sanitárias existentes e encerra o servidor ao fim. Não aceita URL de banco externo e não chama `--apply`. O motor privado do publisher é exercitado apenas com fixtures sintéticas. Dependências opcionais foram instaladas fora do repositório; `package.json`/lockfile não mudaram.

```bash
task_deps="$(mktemp -d)"
npm install --prefix "$task_deps" --ignore-scripts --no-audit --no-fund @electric-sql/pglite@0.5.10 @electric-sql/pglite-socket@0.2.13
SANITARIO_PGLITE_MODULE_ROOT="$task_deps/node_modules" node tests/codex/sanitario-v2-pglite.integration.mjs
```

Referência primária do ambiente: https://pglite.dev/docs/about e https://pglite.dev/docs/pglite-socket. O backend único/multiplexação difere de PostgreSQL convencional; o resultado deste harness não fecha o gate P3/Supabase.
